## ملخص تنفيذي

هذه الوثيقة هي **المرجع الرسمي المعماري** لشجرة تصنيفات Souq Arab EU.  
صُمِّمت لتخدم منصة classifieds عربية في أوروبا على مدى **10–20 سنة** و**ملايين الإعلانات**.

**الهيكل المعتمد:**
- **15 قسمًا رئيسيًا** (لا زيادة قبل بيانات)
- **89 فئة فرعية** (مستويان فقط)
- **مصدر واحد للحقيقة (SSOT)** → DB → API → جميع الشاشات
- **Dynamic Fields** للمواصفات، **ليس** للتصنيفات

# Future Growth Strategy — استراتيجية النمو المستقبلية

## متى نُضيف قسمًا رئيسيًا جديدًا؟

**يجب توفر جميع الشروط التالية:**

1. **حجم:** الفئات المرشحة مجتمعة تتجاوز **~3%** من إجمالي الإعلانات النشطة لربعين متتاليين.
2. **نية مختلفة:** لا يمكن تمثيلها بمعنى واضح ضمن قسم موجود دون تلويته (**>10%** من إعلانات القسم الحالي تصبح شاذة).
3. **بحث مستقل:** المستخدمون يبحثون بمصطلح علوي جديد (بيانات search logs).
4. **موافقة PO:** قرار صريح — ليس تلقائيًا من المطور.

**أمثلة مرشحة مستقبلًا:** معدات تجارية وأعمال · صحة وطب (إن نضج السوق)

---

## متى نُضيف فئة فرعية جديدة؟

**يجب توفر:**

1. **حجم:** **>0.5%** من إعلانات القسم الأم أو **>10,000** إعلان نشط في الفئة المرشحة (أيهما أسبق).
2. **تردد مثبت:** اختبارات مستخدمين أو analytics تُظهر ترددًا أو misclassification متكررًا.
3. **مسار واحد:** الفئة الجديدة لا تُكرر فئة موجودة.
4. **لا تُستبدل dynamic field:** إذا كان الفلتر مواصفة (لون، مقاس) — ابقَ على dynamic field.

**أمثلة مرشحة:** معدات محلات وعرض · نظارات · قوارب ومركبات بحرية

---

## متى نرفض الإضافة؟

1. المنتج له **مكان واضح** في شجرة v3.
2. الحجم **niche** (<0.1% متوقع) — بحث نصي كافٍ.
3. الإضافة تُنشئ **مسارًا ثانيًا** لنفس المنتج.
4. الطلب من فرد واحد أو افتراض — **بدون بيانات**.
5. الإضافة هي **مواصفة** وليست نوع منتج (→ dynamic field).

---

## عملية إضافة فئة (عند استيفاء الشروط)

```
1. اقتراح مكتوب يشير إلى DL المناسب + بيانات الحجم
2. تحديث SSOT (seed-reference-taxonomy.ts)
3. taxonomy:sync على STAGING فقط
4. اختبار EZpad + Playwright — Create Ad / Filters / Search / Category Pages
5. FAIL → Rollback فوري
6. PASS → مراجعة PO → Commit (بموافقة Mohammed)
```

---

## Legacy Sunset Policy

1. `isHidden = true` على الفئة
2. تحقق 7 أيام — لا إعلانات جديدة
3. حذف إن 0 إعلانات مرتبطة
4. لا حذف فئة فيها إعلانات — إعادة توجيه إلزامي أولًا

# Marketplace Design Principles — مبادئ التصميم

هذه المبادئ **ملزمة** ولا تُكسر دون تعديل هذه الوثيقة وموافقة PO.

---

## P-01: مسار واحد لكل منتج/خدمة
لا يوجد منتج شائع له فئتان متنافستان. إن وُجد تضارب → إعادة تسمية أو دمج أو إخفاء — ليس «نترك الاثنين».

## P-02: مستويان فقط
قسم رئيسي → فئة فرعية. لا مستوى ثالث في SSOT أو UI picker.

## P-03: Dynamic Fields للمواصفات — لا للتصنيفات
الماركة، السنة، المساحة، اللون، نوع الجهاز → dynamic fields. نوع المنتج الجذري → فئة فرعية.

## P-04: SSOT واحد
`scripts/src/seed-reference-taxonomy.ts` → `taxonomy:sync` → DB → API → Create Ad / Browse / Filters / Search / Admin / Ad Detail. **لا CATEGORY_TREE محلي في الواجهة.**

## P-05: لا تضخيم بدون بيانات
فئة أو قسم جديد = شروط Future Growth Strategy — ليس رأي مطور أو طلب فردي.

## P-06: فصل نية المستخدم
بيع ≠ إيجار ≠ خدمة ≠ مجاناً ≠ تعليم ≠ مجتمع — كل نية لها قسم أو فئة واضحة.

## P-07: فصل المستهلك عن التجاري الخفيف
معدات مطاعم/ورش منفصلة عن أدوات منزلية — حتى لو تحت نفس القسم الرئيسي.

## P-08: فصل العقار عن السلع
محلات ومكاتب = عقار. معدات المحل = سلع.

## P-09: IDs ثابتة — أسماء قابلة للترجمة
`categoryId` / `subcategoryId` لا تتغير. الأسماء العربية في DB مع i18n EN/DE للعرض.

## P-10: إخفاء قبل الحذف
`isHidden` للتقاعد — لا كسر إعلانات قديمة.

## P-11: subcategoryId إلزامي للإعلانات الجديدة
لا fallback لقسم افتراضي (مثل العقارات).

## P-12: التزامن عبر جميع الشاشات
Create Ad = Category Pages = Filters = Search = Admin — نفس الشجرة من API.

## P-13: القرارات المستقبلية تُوثَّق
أي تغيير بعد v3 → إدخال جديد في Decision Log + تحديث رقم الإصدار.

## P-14: الاختبار قبل الاعتماد
EZpad ADB + Playwright — أي FAIL = Rollback — قبل أي Commit.

## P-15: لا Production دون Staging PASS
STAGING (`qkczposlooaldmsjfmun`) أولًا — Production منفصل صراحةً.

## P-16: Single Canonical Placement — المكان الوحيد
كل منتج أو خدمة شائعة يجب أن يكون لها **مكان واحد واضح فقط** داخل Marketplace.

**القواعد:**
1. إذا استطاع البائع المنطقي وضع نفس المنتج في فئتين أو أكثر بسبب تصميم الشجرة → **خلل معماري** يُصلح قبل التنفيذ أو يُوثَّق في جدول التنسيب الإلزامي (أدناه).
2. الازدواجية بين **نية** (بيع vs خدمة vs مجاناً) مقبولة لأنها أقسام علوية مختلفة — لكن نفس **السلعة المادية** لا تتكرر.
3. عند التعارض: يُطبَّق **جدول التنسيب الإلزامي (P-16 Annex)** — ليس تقدير المستخدم.
4. أي استثناء جديد يتطلب إدخال DL جديد + تحديث الجدول — لا استثناءات شفوية.

**التحقق قبل الإطلاق:** مراجعة المنتجات الشائعة (قسم «P-16 Annex») + اختبار Create Ad على الجهاز.

# Migration Strategy — استراتيجية الهجرة المستقبلية

## الهدف
منع تكرار مشكلة **Legacy** (فئات مكررة/يتيمة خارج SSOT) وضمان أن أي تغيير تصنيف قابل للعكس ومتزامن عبر المنصة.

## 1. مصدر الحقيقة (SSOT)
- **الوحيد:** `scripts/src/seed-reference-taxonomy.ts` متوافق مع هذه الوثيقة.
- **ممنوع:** شجرة محلية في الواجهة (`CATEGORY_TREE` أو غيره).
- **السلسلة:** SSOT → `pnpm run taxonomy:sync` → DB → `GET /api/categories` → جميع الشاشات.

## 2. منع ظهور Legacy جديدة
| آلية | الوصف |
|------|--------|
| **Sync يخفي تلقائيًا** | `taxonomy:sync` يضع `isHidden=true` على أي فئة فرعية في DB غير موجودة في SSOT |
| **Audit دوري** | `pnpm run taxonomy:audit` — يُرفض الدمج إذا `legacySubcategoryCount > 0` ظاهرة في API |
| **Admin** | لا إنشاء فئات من Admin دون تحديث SSOT في نفس PR |
| **CI (مستقبلي)** | مقارنة عدد الفئات API مع `referenceTaxonomySubcategoryCount()` |

## 3. نقل الإعلانات القديمة عند تغيير التصنيف

```
المرحلة 0: taxonomy:audit — عدد الإعلانات على الفئة المراد إخفاءها
المرحلة 1: إنشاء/تأكيد الفئة البديلة في SSOT
المرحلة 2: taxonomy:sync
المرحلة 3: جدول mapping (legacy_sub_id → canonical_sub_id) — موثّق في DL
المرحلة 4: UPDATE ads SET subcategory_id = :canonical WHERE subcategory_id IN (:legacy)
المرحلة 5: isHidden=true على legacy
المرحلة 6: تحقق 7 أيام
المرحلة 7: DELETE legacy WHERE ad_count = 0
```

**قواعد الأمان:**
- لا `DELETE` لفئة فيها إعلانات.
- لا Production قبل Staging PASS.
- Dry-run: `SELECT count(*)` قبل كل `UPDATE`.

## 4. تحديث Search
- Search يعتمد `categoryId` + `subcategoryId` من DB — **لا أسماء نصية ثابتة**.
- بعد الهجرة: إعادة فهرسة غير مطلوبة إذا كانت الفهارس على IDs (الوضع الحالي).
- تحقق: بحث بفلتر `subcategoryId` الجديد يعيد الإعلانات المنقولة.

## 5. تحديث Filters
- Filters تقرأ من نفس API — تزامن تلقائي بعد sync.
- تحقق: Category Page `?subcategoryId=` لكل فئة متأثرة.

## 6. تحديث Category Pages
- Routes: `/category/:categoryId` — ثابت.
- عناوين الفئات من API — لا hardcode.

## 7. تحديث Create Ad
- Picker من API فقط — `subcategoryId` إلزامي.
- تحقق: EZpad Create Ad — لا أسماء legacy ظاهرة.

## 8. تحديث Ad Detail
- يعرض `categoryName` / `subcategoryName` من API.
- بعد هجرة الإعلانات: التحقق من عينة إعلانات قديمة.

## 9. Rollback كامل عند الفشل

```
1. git checkout -- scripts/src/seed-reference-taxonomy.ts
2. taxonomy:sync (استعادة SSOT السابق)
3. UPDATE subcategories SET is_hidden = false WHERE id IN (:rolled_back) — إن لزم
4. استعادة ads.subcategory_id من snapshot SQL — إن تمت هجرة
5. إعادة تشغيل اختبارات EZpad + Playwright
6. توثيق الحادثة في Decision Log
```

**لا Commit** على حالة فاشلة.
